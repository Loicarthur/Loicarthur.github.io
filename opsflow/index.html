OPSFLOW

Un SaaS B2B multi-tenant de gestion d'incidents et de workflows automatisés, avec contrôle d'accès par rôles, moteur de règles piloté par les données et pipeline CI/CD complet.

01 — The problem

Des incidents qui se perdent, des actions refaites à la main.

Dans une équipe support ou IT, les demandes arrivent de partout : e-mails, messages, tableurs. Personne ne sait qui traite quoi, les délais dérapent sans alerte, et chaque ticket urgent demande les mêmes gestes manuels : assigner, prévenir, relancer.

CentraliserUn seul endroit pour les ticketsChaque organisation suit ses incidents et demandes, avec statut, priorité et responsable.
ContrôlerQui peut faire quoiDes rôles clairs, du propriétaire au simple lecteur, appliqués partout.
AutomatiserLes gestes répétitifsDes règles « si… alors… » qui assignent, notifient ou clôturent sans intervention.
02 — The product

Le cycle complet, de l'inscription à l'audit.

01 Authentification & multi-tenant L’inscription crée une organisation et son propriétaire. Sessions JWT avec refresh token rotatif et révocable.
02 Rôles & permissions 5 rôles (Owner, Admin, Manager, Agent, Viewer), invitations par e-mail, changement de rôle, retrait de membres.
03 Tickets Création, assignation, résolution, filtres, recherche, tri et pagination.
04 Workflows automatisés Règles « si… alors… » déclenchées par les événements des tickets, extensibles sans toucher au code.
05 Jobs asynchrones File de jobs avec retries exponentiels et tâches différées, comme une clôture automatique après X heures.
06 Notifications Dans l’application et par e-mail via SMTP générique, sans dépendance à un fournisseur.
07 Audit log Chaque action sensible est tracée : auteur, état avant et après, horodatage.
08 Dashboard & API Tickets par statut et priorité, SLA en retard, activité récente. API REST documentée avec Swagger.
03 — Technical architecture

Chaque couche à sa place.

Un monorepo en trois paquets. Aucune logique métier dans les contrôleurs ni dans les composants React, un seul point d'accès aux données, et des permissions définies une fois puis partagées entre le front et le back.

Frontend · apps/webNext.js 16 (App Router), React 19, Tailwind v4, shadcn/ui. Un client API unique qui gère le JWT et son renouvellement transparent.
API · apps/apiNestJS 12 en TypeScript strict. Logique métier dans les services, validation des entrées, guards RBAC, rate limiting, Swagger.
Partagé · packages/sharedMatrice des permissions et énumérations, utilisées à l'identique par l'API et par l'interface.
PostgreSQL 17 · Prisma 6Données relationnelles, règles de workflow stockées en JSON, un seul point d'accès (PrismaService).
Redis 7 · BullMQJobs asynchrones avec retries exponentiels et tâches différées.
Livraison Push / PR→ Typecheck · lint · migrations→ Tests Vitest→ Build→ E2E Playwright→ Docker multi-stage
04 — Workflow engine

Des règles en données, pas en dur.

Une règle, c'est « SI (conditions) ALORS (actions) », stockée en base et déclenchée par un événement sur un ticket. Ajouter un nouveau type d'action, c'est ajouter une seule fonction : aucune règle n'est codée en dur.

01 · DéclencherÉvénement ticketCréation, changement de statut ou de priorité.
02 · ÉvaluerÉvaluateur de conditionsLes conditions JSON de chaque règle sont testées sur le ticket.
03 · OrchestrerWorker BullMQExécution asynchrone, retries, jobs différés comme une clôture après X heures.
04 · AgirRegistre d'actionsAssigner, notifier, changer un statut, appeler un webhook signé.
05 — Challenges solved

Du vrai débogage, pas seulement du code généré.

Les problèmes les plus intéressants sont apparus en faisant tourner la stack complète et la CI pour de vrai.

Une CI rouge depuis le premier commit Le pipeline échouait à chaque exécution. Diagnostic étape par étape, puis correction de l’ordre des étapes et des dépendances entre jobs.
Un lockfile réservé à Windows Le lockfile ne contenait que des binaires natifs Windows : l’installation cassait sur les runners Linux. Régénéré pour toutes les plateformes.
Des tests E2E sans backend Les tests Playwright tournaient contre une API qui n’était jamais démarrée. Les services sont désormais lancés avant les tests.
Des bugs révélés par la stack complète Faire tourner l’ensemble de bout en bout pour la première fois a fait apparaître des bugs invisibles en isolé, corrigés dans la foulée.
Un réflexe de sécurité sur le code généré Un fichier d’instructions généré par un outil tentait de faire installer un outil de télémétrie non demandé. Repéré à la relecture et supprimé.
06 — Architecture decisions

Des choix assumés, sans sur-ingénierie.

Workflows data-driven Conditions et actions stockées en JSON dans PostgreSQL plutôt que des règles codées en dur.
Refresh tokens hashés et rotatifs Rotation à chaque usage : un token volé n’offre qu’une fenêtre d’utilisation unique avant détection.
SMTP générique Nodemailer plutôt qu’un SDK propriétaire : le projet est pensé pour être auto-hébergé avec Docker.
Monorepo npm workspaces Suffisant pour trois paquets, sans ajouter Turborepo ou pnpm : pas de sur-ingénierie.
